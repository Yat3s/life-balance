# 早晚高峰车位回顾

## 功能与边界

原停车卡片只增加“早晚高峰车位回顾”入口（新版 `commuteV2` 和旧版
`commute` 都支持），不重做首页、卡片布局或底部导航。点击后进入独立页面，
沿用现有字体、浅色卡片及蓝色数据线。可切换 B25 / 中盟；
日期控件只提供**过去7个完整自然日**，即北京时间昨天至7天前，不含今天。
默认打开昨天，可用“7天前 / 回到昨天”快速切换两个边界日期。
服务端独立执行相同限制，修改客户端或增加物理保留期也不能查询今天、未来或更早日期。

页面不称为全天历史或全天热力图：早、晚高峰分别有自己的卡片和横轴，
只展示各自窗口内的剩余车位曲线。点按或拖动曲线可查看附近的实际采样；
缺失处不连线，也不插值编造余位。没有记录显示“—”，真实零余位显示“0”。
“最低记录”是所选时段实际观测的最小值；“末次记录”是最后采到的一笔，
都附采样时刻，**不是实时余位，也不是精确停满时刻**。

默认只在**工作日**的两段高峰采集，起止点均包含：

| 时段 | 北京时间 | 请求间隔 | 每工作日记录 |
| --- | --- | --- | --- |
| 早高峰 | 07:30–10:30 | 5 分钟 | 37 条 |
| 晚高峰 | 16:30–19:30 | 10 分钟 | 19 条 |

两段之外不请求停车接口；午间空白是**不安排采集**，不是漏采。
两个时段各有独立曲线，午间既不占横轴，也不会被解释成漏采。法定假期自动跳过，
周末调休补班自动采集，**不需要手工维护 `skipDates`**。

仅展示实际记录数，不凭配置假定采样完整率。空时段保留卡片并用“—”说明，
不把空值当零，也不显示今天的未完成时段或宣称采集服务在线。
历史采样间隔按记录自身说明。若调整 INI 后旧记录落在当前窗口外，页面显式说明
不展示的条数，不把这些旧数据塞回午间图轴；数据本身仍由正常保留策略管理。

不会改变现有实时余量刷新、缓存、滚动数字或 `parking-full` 停满时间功能。
既有 `parking-full` 仅记录阈值/停满时间，不能还原完整余量历史。
**新历史只会从启用定时器之后开始累积，没有部署前的完整历史。**

## 调用链

```text
腾讯云定时器 parking-history-collect
  → cloudfunctions/parkingHistory/index.js
  → history.js: createHandler / 先匹配 INI 配置的采样槽
  → workdays.js: 自动读取/刷新中国工作日日历，判断法定假期和调休
  → source.js: fetchSpaces / parseSpaces
  → 同现有实时功能的 ParkingSpaceApi/GetData（一次请求提取两处余量）
  → 当前 CloudBase 环境的 parking-history 集合

停车卡片 toParkingHistory
  → pages/router.js: navigateToParkingHistory
  → pages/home/parkinghistory/parkinghistory.js: loadHistory
  → repository/dashboardRepo.js: fetchParkingHistory
  → repository/baseRepo.js: cloudFunctionCall
  → parkingHistory 云函数 action=history（仅查询数据库，不访问上游）
  → model.js 按当前高峰窗口筛选、计算实际最小值/末次值
  → 早、晚各自独立的 canvas 曲线和状态卡片

独立每日定时器 parking-history-cleanup
  → 同一云函数的清理分支
  → 仅删除 parking-history 中早于保留边界的记录
```

云函数用 `cloud.DYNAMIC_CURRENT_ENV`，客户端继续使用 `miniprogram/app.js`
已有的环境选择。**数据存在这个腾讯 CloudBase 环境的云数据库中，不是小程序
本地缓存、仓库文件或服务器磁盘，也不需要新建数据库服务。**
开发者须确认 fork 使用自己的测试环境，不要直接部署进他人的现有环境。

## 存储形状与成本

新增专用集合名固定为 `parking-history`，一条文档合并两个停车场：

```json
{
  "_id": "2026-10-26-540",
  "date": "2026-10-26",
  "minute": 540,
  "sampledAt": 1792976400000,
  "window": "morning",
  "intervalMinutes": 5,
  "b25": 123,
  "zhongmeng": 45
}
```

这是形状示例，不是实测数据。`date`、`minute` 是北京时间的日期和当日分钟数；
`sampledAt` 是请求返回后的 Unix 毫秒时间戳。ID 固定为“日期-采样槽”，
同槽重试覆盖同一文档，避免重复增长；保存时段名称及实际采样间隔，
以便后续调整配置时识别曲线缺口。
接口只返回图表所需字段，不暴露数据库 ID。

默认每个工作日最多 **37 + 19 = 56 条**，两个停车场不会翻倍。
普通五工作日的一周为 280 条。调休可能使周末成为工作日，
因此按最保守情况，7日可见窗口最多 **392 条**。存储还需保留正在采集的今天，
默认物理保留8个自然日，全部为工作日时最多 **448 条**。
按每条逻辑载荷约 200–500 字节粗估约 90–224 KB；
数据库元数据、索引、计费单位、日志和失败积压另计，不能视作账单保证。
若扩大到全天、保留期 31 天，成本会相应增加。

自动日历使用单独的 `parking-calendar` 集合，固定文档 ID 为 `china-workdays`，
保存当前年份的已验证假期/补班覆盖表、公告链接、刷新时间和短暂故障重试时间。
只有一条缓存文档，跨年自动覆盖，不会每年新增文档。多个云函数实例共享该缓存，
同一实例还有内存缓存及合并并发刷新，正常情况下每 24 小时更新一次，
只读取当前年、下一年两个公开 JSON 文件，不会每次采样都请求日历网站。

采集基础定时器每五分钟全天触发（288 次/日），先在内存匹配采样槽；
不在早晚两段采样槽内时，**不请求停车接口、不查询日历，也不读写数据库**。
清理每天触发一次，因此默认每 30 天约 8,670 次函数调用。
真正的停车请求在工作日内最多 56 次/日；非工作日只判断日历，不发停车请求。
保留基础触发器可让修改 INI 中的两个窗口直接生效，无需重新计算 cron 表达式。
定时器平台重试可能额外请求上游，但不会新增重复文档。

## 配置与修改

**只编辑 `cloudfunctions/parkingHistory/parking-history.ini`，然后重新部署云函数。**
`config.js` 只是读取它的加载器，不再放业务配置；无需编辑 JS 或手工设置跳过日期。

```ini
[morning]
start = 07:30
end = 10:30
interval_minutes = 5

[evening]
start = 16:30
end = 19:30
interval_minutes = 10

[storage]
retention_days = 8

[calendar]
refresh_hours = 24
max_stale_hours = 168
```

`[morning]` 与 `[evening]` 完全独立，`start` / `end` 格式为 `HH:MM`，
起止点均采样；例如默认早段是 07:30、07:35……10:30，晚段是
16:30、16:40……19:30。间隔相对于每段的起点，而不是相对于午夜。

时间须对齐五分钟，间隔可为 5、10、15、20、30、60 分钟，
时段长度须能被间隔整除；早段必须在晚段之前，两段不能重叠，
不支持跨午夜窗口。`retention_days` 允许 8–31。
日历刷新频率 `refresh_hours` 为 1–168 小时，
最大可用缓存年龄 `max_stale_hours` 不得小于刷新频率且不得超过 744 小时。
重复键、未知键、缺项或不合法配置会报错，不会静默采用默认值。
INI 支持独立节、键值及 `;` / `#` 注释，不支持插值或执行代码。

时区固定为 **Asia/Shanghai / UTC+08:00**：`history.js` 和前端 `model.js`
使用 UTC 算法加固定八小时偏移，不依赖客户端所在地或服务器本地时区。
苏州没有夏令时；本功能不扩展成通用跨时区调度系统。

### 工作日如何自动判断

`workdays.js` 使用 [NateScarlet/holiday-cn](https://github.com/NateScarlet/holiday-cn)
的公开中国法定节假日数据（MIT），该项目每日抓取国务院公告。
这是**第三方整理的数据集，不是政府实时 API**；每次刷新先通过 HTTPS
读取 GitHub Raw，不可用或数据不合法时尝试 jsDelivr 镜像。
只发送年份，不发送用户身份、车牌或停车余量。

判断顺序为：

1. 公告表标为休息日：不采集，即使当天是周一至周五。
2. 公告表标为调休工作日：采集，即使当天是周六或周日。
3. **已取得有效的该年公告表**，但当日无特别安排：按普通周一至周五判断。

同时读取下一年的公告表，因为下一年安排可能覆盖本年十二月的日期。
下一年文件不存在（两处均 404）或明确为空表示尚未发布，
不影响当前已发布年份；但**当前年份缺失、为空、错误年份或不合法时绝不猜测**。
校验年份、有效公告来源链接、真实日期、布尔休息标记和冲突覆盖记录。
新年会自动请求新年份，下一年公告发布后日常刷新自动生效，不需要每年改配置。

默认刷新每 24 小时一次。源短暂故障时，可使用年龄不超过 168 小时的
已验证同年缓存，并记录 warning；失败刷新至少等待一小时再尝试，
重试退避时间也写入共享缓存，避免多个冷实例每五分钟重复请求。
缓存过旧、不可用或与当前年份不符且刷新失败时，**本次停车采集停止并抛错**；
下一采样槽自动重试，不会假装工作日判断成功。存储缓存失败也会记录 warning，
若已取得合法在线日历则本次仍可采样，并暂用实例内存缓存。
节假日临时调整的生效时间受数据源发布、镜像同步和缓存刷新周期影响。

**查询范围和物理保留期不是一回事。** 对北京时间今天 D，
查询只允许 D−7…D−1，共7个完整自然日；`earliest` 固定为 D−7，
`latest` 固定为 D−1。日期选择器仅有这7项，不提供全部历史日历。
今天 D 的数据继续正常采集，但直到次日才能作为完整自然日查看。
因此默认物理保留 D−7…D 共8天：7天历史加今天的在途采集。
即使把物理保留期加长到31天，查询和页面仍然只能看到前7个完整自然日。
缩短保留期前应确认可接受不可逆的数据删除，必要时由环境所有者先导出备份。

`cloudfunctions/parkingHistory/config.json` 定义两个独立定时器：

- `parking-history-collect`：`0 */5 * * * * *`，每五分钟。
- `parking-history-cleanup`：`0 5 0 * * * *`，平台调度时区的每天 00:05。

七字段格式沿用仓库 `cloudfunctions/luckDraw/config.json` 的模式。
部署后必须在控制台核对其实际启用状态、表达式及平台时区，
建议使用北京时间。每五分钟触发不受整小时时区偏移影响；
清理始终按执行当时的北京时间计算边界，不依赖调度器的日历日期。
不要只修改控制台而让仓库配置失真。当前支持的采样间隔无需修改基础触发器；
如需要低于五分钟，必须同时修改校验、触发器和成本估算，不是直接填 `1`。
从旧版升级时必须把现有采集定时器从十分钟更新为五分钟，否则会漏掉早段一半采样槽。

## 清理与安全边界

以执行时北京时间日期 D 为准，仅选择
`date < D − (retentionDays − 1)` 的新集合文档；边界当天完整保留。
即使周末、假期或关闭采集，独立每日清理仍可运行。
每批最多 100 条，至多五批，即每次最多 500 次定向删除；
到达上限记录 warning，后续每日调用继续清理。默认每日过期量最多 56 条。
修改为更大窗口/更短保留期可能产生积压，应监控而不是无限循环删除。

**逻辑查询窗口有界，不等于保证到期时物理立即删除。**
停用定时器、平台故障、索引/权限错误或删除失败都可能延迟物理清理；
查询仍拒绝窗口外日期。错误向平台抛出并写日志，不转换成成功。
部署者应为云函数失败和清理上限 warning 配置监控/告警，并核查数据库存量。
无法声称仅凭本代码就能保证硬性存储上限。

采集/清理只接受 Timer 事件、两个固定 TriggerName，且拒绝 SDK 返回的
客户端 OPENID / APPID / UNIONID 或非服务端调用 SOURCE。
**客户端传入 Type/TriggerName 不能代替可信调用身份**；身份取自 SDK，
不从 event 取。云端服务账号/控制台管理员属于信任边界，应使用最小 IAM 权限。
不应开放无认证 HTTP 云函数入口，也不应设置伪造或清空调用身份的网关。
上线时需实际确认 Timer 的身份上下文可通过校验，并验证小程序伪造事件被拒绝。

两个新增集合都设置为“所有用户不可读写”（客户端权限规则为 `read: false`、
`write: false`），由云函数服务端访问；历史通过只读 action 提供。
集合名固定，查询只接受严格格式的保留期内日期，调用方不能指定集合、
删除条件或任意查询。每日清理仅操作 `parking-history`，不操作日历缓存；
日历缓存仅覆盖固定文档，新增逻辑**不读写或删除**已有 `parking-full`、用户数据等集合。
SDK 的服务端权限可绕过客户端规则，因此代码审查和 IAM 权限仍然重要。

上游响应必须同时包含两处非负整数余量，缺项、重复项、格式错误、HTTP 非 200、
8 秒超时或过大的响应都会失败，不会写入“0”冒充有效数据。
停车源沿用现有公开 HTTP 地址，链路本身不提供 TLS 完整性保障；
自动日历新增只读 HTTPS 数据源，不需要 API key、注册账号或新数据库服务。
不进行历史回填或自动高频重试。

## 部署顺序（需要环境所有者执行）

1. 在微信开发者工具选择**自己有权限的测试 CloudBase 环境**，核对客户端
   `miniprogram/app.js` 的环境与部署目标一致。
2. 新建集合 `parking-history` 及 `parking-calendar`，都禁止客户端直接读写；为历史集合创建复合索引
   `date` 升序 + `minute` 升序，并确保日期范围清理查询有可用索引
   （必要时另建 `date` 升序索引）。不要更改旧集合权限。
3. 如需改采样时段，编辑 `parking-history.ini`；**无需配置任何节假日**。
   上传部署 `parkingHistory`，确保 INI 文件一并上传，
   由云端安装依赖。使用 Node.js 16 或更新的受支持运行时，建议 Node.js 18+；
   云函数超时建议 60 秒，预留最多 500 次删除的时间。
   本地 Node.js 测试使用 22，无需为图表引入 npm 依赖。
4. 安装并启用 `config.json` 两个触发器；不要假设仅上传代码就已部署触发器。
   在控制台核验触发器名称和时区，采集表达式应为 `*/5` 而非旧版的 `*/10`，
   不能改名后仍沿用旧处理代码。
5. 在工作日高峰时间窗内观察真实定时触发，确认日历缓存、日志、两个余量和文档 ID；
   在测试环境验证客户端伪造 Timer 请求被拒绝。使用合成过期数据核查
   清理边界与日常清理日志。不要用生产集合做删除实验。
6. 编译小程序并发布体验版：检查原首页及两版入口保持不变、日期选择、B25/中盟切换、早晚独立曲线、
   7天前/回到昨天、今天及更早日期被拒绝、跨午夜日期轮转、零余量、无记录、
   失败重试、缺口不连线、曲线点选、
   小屏布局以及实时卡片/停满时间无回归。确认无误后再发布正式版。

新云函数须先于客户端发布，否则历史页会显示加载失败及重试。
现有 `uploadCloudFunction.sh` 含旧环境/绝对路径，不是本功能的部署命令。
卸载时先停用两个触发器及入口；是否删除两个专用集合由环境所有者决定，
不提供批量删除其他集合的脚本。
